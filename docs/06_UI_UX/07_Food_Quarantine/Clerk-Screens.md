**المكونات (الموجودة فعلاً في `components/`):**
- `StatCard` (`components/common/StatCard.tsx`) للبطاقات الإحصائية.
- `PageHeader` للعنوان + زر الإنشاء.
- `DataTable` (`components/ui/DataTable.tsx`) — **وليس MUI DataGrid** (غير مثبت في المشروع).
- زر إنشاء ينقل إلى معالج الخطوات.

**مصدر البيانات (مطلوب ربطه):**
- إحصائيات الكاتب: نقطة نهاية مقترحة `GET /api/v1/food/clerk/stats/?port={port_id}` (عدّادات على FoodShipment حسب recorded_by/port/التاريخ).
- أحدث المعاملات: `GET /api/v1/food/shipments/?recorded_by=me&page_size=10`.

**التفاعلات:**
- النقر على بطاقة → قائمة المعاملات المصفاة بالحالة.
- النقر على صف → صفحة التفاصيل.
- بطاقة «بانتظار التحصيل» عرض فقط — لا زر تحصيل (الصلاحية للمحاسب).

## 2. قائمة المعاملات

**المسار المستهدف:** `/app/clerk/requests`
**الهدف:** عرض جميع المعاملات التي أنشأها الكاتب مع تصفية.

### التخطيط

```
┌─────────────────────────────────────────────────────────────┐
│  PageHeader: المعاملات – رقابة الأغذية                       │
├─────────────────────────────────────────────────────────────┤
│  FilterBar: [بحث: رقم البيان/المستورد] [نوع وارد/صادر]      │
│  [وسيلة النقل] [الحالة] [التاريخ من/إلى]                     │
├─────────────────────────────────────────────────────────────┤
│  DataTable:                                                  │
│  | رقم البيان | النوع | وسيلة | المستورد | الأصناف | الحالة | تاريخ | إجراء | │
│  ترقيم صفحات (مدعوم افتراضياً في DataTable)                   │
└─────────────────────────────────────────────────────────────┘
```

**ألوان حالات StatusChip — بالـ enum الفعلي (`FoodShipment.ShipmentStatus`):**

| الحالة | اللون | tone |
|---|---|---|
| `DRAFT` *(مقترح)* | رمادي | default |
| `RECEIVED` (= REGISTERED سابقاً) | أزرق فاتح | info |
| `FEES_DUE` (= AWAITING_PAYMENT سابقاً) | أصفر | warning |
| مدفوعة → `AWAITING_INSPECTION` | أخضر فاتح | success |
| `UNDER_INSPECTION` | بنفسجي | primary |
| عينات مأخوذة / `AWAITING_LAB_RESULTS` | برتقالي/أزرق | info |
| `AWAITING_DECISION` (= UNDER_REVIEW) | نيلي | secondary |
| `RELEASED` (= COMPLETED) | أخضر | success |
| `REJECTED` / `HOLD` / `DESTROYED` | أحمر | error |

**التفاعلات:**
- زر «عرض» → صفحة التفاصيل.
- إذا كانت الحالة `DRAFT`: زر إضافي «تعديل» → المعالج بنفس السجل.
- الحذف متاح فقط لـ `DRAFT` ومن صفحة التفاصيل مع `ConfirmDialog`.

## 3. معالج إنشاء معاملة (Wizard)

**المسار:** Dialog داخل `/app/clerk-dashboard`
**الهدف:** إدخال بيانات المعاملة خطوة بخطوة حتى الإرسال.

### التنقل بين الخطوات
`MUI Stepper` أفقي بثماني خطوات:
1. **نوع الطلب**: وارد IMPORT / صادر EXPORT
2. **بيانات الشحنة**: وسيلة النقل، الميناء، تاريخ الوصول، البوليصة
3. **البيانات الحكومية**: رقم البيان الجمركي، شهادة الاعتماد
4. **المستورد/المصدر**: بيانات الشركة والمية المستوردة
5. **المنتجات**: إضافة الأصناف مع سياسة العينات التلقائية
6. **المستندات**: رفع المستندات الإلزامية والاختيارية
7. **الرسوم والعينات**: عرض تلقائي للرسوم وسياسة العينات
8. **المراجعة والإرسال**: ملخص الطلب وزر الإرسال

يمكن للكاتب التقدم حتى الخطوة 7 والرجوع للتعديل قبل الإرسال.

### الخطوة 1: معلومات المعاملة
- نوع المعاملة: `RadioGroup` (وارد IMPORT / صادر EXPORT).
- وسيلة النقل: `RadioGroup` مربوطة بأنواع `Conveyance` (جوي PLANE / بحري SHIP / بري TRUCK أو REFRIGERATED_TRUCK).
- المنفذ: حقل معطل يُملأ من نطاق حساب الكاتب (`RoleAssignment` → PORT) ويُحفظ في `shipment.port`.

### الخطوة 2: بيانات الشحنة

تتبدل الحقول حسب وسيلة النقل:

**للبحري (الحقول الموجودة فعلاً):**
- اسم السفينة `vessel_name`, ميناء الشحن `loading_port`, رقم B/L `bill_of_lading`, تاريخ الوصول, الوزن.

**للجوي (تُخزن في `transport_data` المقترح):**
- شركة الطيران، رقم الرحلة، مطار الإقلاع، AWB، عدد الطرود، الوزن، التاريخ.

**للبري (تُخزن في `transport_data` المقترح):**
- رقم الشاحنة، رقم اللوحة، المعبر، الوزن، بيانات الرحلة.

### الخطوة 3: البيانات الحكومية
- رقم البيان الجمركي `customs_number` — يدوي حالياً (🔗 ربط مستقبلي مع Customs API).
- رقم الشهادة الصحية/الاعتماد `certificate_no`.
- مؤشر حالة: 🟡 إدخال يدوي / تحقق داخلي.

### الخطوة 4: بيانات المستورد / المصدر
- `Autocomplete` يبحث في `Supplier` / `Exporter` (بالاسم أو الرقم الضريبي).
- عند الاختيار تُعرض بيانات الشركة معطلة (تعبئة تلقائية).
- زر «إضافة شركة جديدة» يفتح `FormDialog` مصغراً ثم يختار الشركة تلقائياً.
- الحقول تُحفظ كأسماء على الشحنة (`supplier_name`, `exporter_name`, `clearing_agent`) — ويُوصى بإرسال الـ id أيضاً للربط المستقبلي بمحرك المخاطر.

### الخطوة 5: بيانات المنتج
- جدول الأصناف المضافة + زر «إضافة صنف» يفتح `Autocomplete` على كتالوج `FoodProduct`.
- اختيار المنتج يُعبئ تلقائياً: التصنيف الغذائي، بلد المنشأ، نوع العبوة.
- يُدخل الكاتب: عدد العبوات، الوزن (كجم).
- يمكن إضافة أكثر من صنف (بنود `FoodOrderItem`).
- ⚠️ حتى تنفيذ ربط FK: تُرسل أسماء الأصناف نصاً كما يتطلب `_replace_items()` الحالي.

### الخطوة 6: المستندات
- قائمة تحقق `CheckboxList`: البيان الجمركي، الشهادة الصحية، شهادة المنشأ، الفاتورة، Packing List، AWB/B/L، شهادة التحليل (اختياري)، مستند إضافي.
- عند التحديد يظهر زر رفع ملف؛ المرفقات تُدار بقائمة مع حذف.
- ⚠️ يعتمد على نموذج `ShipmentAttachment` المقترح — قبل تنفيذه تبقى القائمة محلية في الواجهة (مسودة فقط).

### الخطوة 7: الرسوم (عرض تلقائي)
- جدول الرسوم يُجلب من: `GET /api/v1/food/shipments/{id}/fee-preview/` الذي يستخدم قواعد `QuarantineFee`.
- البنود النموذجية: رسوم رقابة، رسوم عينات/معمل، رسوم شهادات + الإجمالي.
- الحالة: 🟡 بانتظار التحصيل (`FEES_DUE`).
- **لا أزرار تعديل إطلاقاً** — فقط زر «إعادة حساب» يستدعي fee-preview مجدداً.
- الحساب يتم في الخلفية دائماً؛ لا منطق رسوم في الواجهة.

> 💡 تدفق عملي مقترح: حفظ الشحنة كمسودة أولاً للحصول على id ثم جلب fee-preview في الخطوة 7.

### الخطوة 8: المراجعة والإرسال
- ملخص ببطاقات صغيرة: بيانات الشحنة، الأطراف، الأصناف، المستندات، الرسوم.
- زران:
  - 💾 **حفظ مسودة** (ثانوي) → `POST/PATCH` مع `status=DRAFT` *(يتطلب إضافة الحالة)*.
  - 📤 **إرسال** (أساسي) → action `submit` → `RECEIVED` (+ `FEES_DUE` عند استحقاق الرسوم).
- عند الإرسال يظهر `ConfirmDialog`: «سيتم إرسال المعاملة إلى مرحلة الاستلام والتحصيل، هل تريد المتابعة؟»

**التحقق من الصحة:**
- جميع الحقول الإلزامية يجب أن تكون مكتملة قبل الإرسال.
- عند وجود أخطاء: تمييز الحقول وتوجيه المستخدم للخطوة الناقصة (Stepper مع خطأ).

## 4. صفحة تفاصيل معاملة

**المسار:** `/app/food/shipments/:id` (ShipmentWorkflowPage الموجودة)
**الهدف:** عرض كامل للبيانات مع شريط سير العمل وسجل العمليات.

### التخطيط

```
┌─────────────────────────────────────────────────────────────┐
│  < رجوع    معاملة {manifest_number}    [تعديل — DRAFT فقط]  │
├─────────────────────────────────────────────────────────────┤
│  StatusChip: 🟡 FEES_DUE بانتظار التحصيل                    │
│                                                              │
│  ── بيانات الشحنة ──   ── المستورد/المورد ──                │
│  ── الأصناف (DataTable) ──   ── المستندات ──                │
│  ── الرسوم (fee-preview) ──   ── العينات إن وجدت ──          │
│                                                              │
│  ── سير العمل (MUI Stepper أفقي) ──                          │
│  مسودة* ← استلام ← رسوم مستحقة ← تفتيش ← نتائج ← قرار       │
│  (المرحلة الحالية مظللة — حسب enum الحالة الفعلي)           │
│                                                              │
│  ── سجل العمليات (AuditLog) ──                               │
│  التاريخ | المستخدم (الدور) | الإجراء                        │
└─────────────────────────────────────────────────────────────┘
```

**الأزرار والتفاعلات:**
- «تعديل» يظهر فقط لحالة `DRAFT` — لا أزرار تغيير حالة للكاتب إطلاقاً.
- النقر على مستند يفتحه/يحمّله (بعد تنفيذ المرفقات).
- AuditLog يعرض المستخدم والدور والتوقيت لكل حدث.
