# FCLIS — Functional Specification (مواصفة نظام معلومات المختبر لمراقبة الأغذية)

> This document captures the approved functional specification for the Food Control Laboratory
> Information System (FCLIS). It is the authoritative design reference for the laboratory module:
> sample classification, sources catalog, chain of custody, versioned microbiological specifications
> with the n/c/m/M evaluation engine, separation of duties, and external-stakeholder integration.

## <a id="overview"></a> 1. نظرة عامة

النظام معلومات المختبر لمراقبة الأغذية (Food Control Laboratory Information System) هو النظام
الرقمي الذي يدير دورة عمل العينات الغذائية داخل المختبر الاتحادي، من لحظة الاستلام وحتى إصدار
الشهادات وتسليم النتائج للأطراف الخارجية، مع ضمان:

- **قابلية التتبع الكامل** لكل عينة عبر سلسلة الحيازة غير القابلة للتعديل.
- **فصل المهام (Separation of Duties)** بين أدوار الاستقبال والتنسيق والتحليل والمراجعة والاعتماد.
- **التقييم الآلي للنتائج** وفق المواصفات الميكروبيولوجية الوطنية بنظام (n/c/m/M) القابل للإصدار.
- **خط مراجعة جودة (QA) مستقل** عن خط الإنتاج.
- **التكامل مع الأطراف الخارجية** (الرقابة الغذائية، التفتيش، الترصد، الجمارك، المالية، المعايير،
  الموانئ والمطارات) عبر واجهات برمجة (API) وأحداث وتقارير.

## <a id="sample-classification"></a> 2. تصنيف العينات

تُقسَّم العينات إلى صنفين رئيسيين، لكل منهما دورة حياة وإجراءات مختلفة:

### 2.1 العينة المرجعية (Reference Sample)

- عينة تُحفظ لأغراض مرجعية/تحكيمية وتستخدم للتحقق من صحة النتائج عند النزاع.
- لها **رمز موحّد (coding)** وحفظ وفق شروط محددة وفترة احتفاظ محددة.
- قد تُسحب (retrieve) للتأكيد أو تُتلف (discard) بعد انتهاء صلاحيتها المرجعية مع توثيق السبب.

### 2.2 عينة التحليل (Analysis Sample)

- العينة التي تخضع لدورة التحليل المخبري الكاملة وتنتج عنها النتائج والشهادات.
- تمر بمراحل الاستلام والتنسيق والإسناد والتحليل والمراجعة والاعتماد والتفريغ (dispatch).

المصدر **حقل كتالوجي** (Foreign Key) على العينة، وليس نصاً حراً، لضمان توحيد التقارير والتحليلات.
المصادر المعتمدة:

| الرمز | المصدر | ملاحظات |
| --- | --- | --- |
| AIRPORT | المطار | وصولات الطيران |
| FREE_ZONE | المنطقة الحرة | |
| NORTH_PORT | ميناء السودان (الشمالي) | |
| SOUTH_PORT | ميناء السودان (الجنوبي) | |
| OSEIF_PORT | ميناء أوسيف | |
| DIGNIA_PORT | ميناء الأمير عثمان دقنة | |
| FIELD_INSPECTION | تفتيش ميداني | |

| GOVERNMENT | جهة حكومية | |
| OTHER | أخرى | مذكورة النص عند الحاجة |

يدعم الكتالوج الإنشاء والتعديل والحذف عبر لوحة تحكم النظام، ويُستخدم في كل التقارير التجميعية.

## <a id="sample-lifecycle"></a> 4. دورة حياة العينة

دورة الحياة الخطية عبر المراحل التالية، وكل انتقال يُسجَّل كحدث في سلسلة الحيازة:

```
استلام (Reception) → تنسيق/توزيع (Coordination) → إسناد محلل (Assignment)
→ تحليل وإدخال نتائج (Analysis) → مراجعة رئيس القسم (Section Head Review)
→ مراجعة الجودة (QA/QC) → اعتماد مدير المختبر (Lab Director Approval)
→ إصدار شهادة/تفريغ (Certification / Dispatch)
```

### قرارات الاستلام

| القرار | الوصف |
| --- | --- |
| قبول (ACCEPTED) | العينة مطابقة للمتطلبات |
| قبول مشروط (CONDITIONALLY_ACCEPTED) | عيوب غير جوهرية قابلة للمعالجة |
| رفض (REJECTED) | عيوب جوهرية مع توثيق السبب |

### حالات العينة (LifecycleStatus)

`RECEIVED → COORDINATED → ASSIGNED → UNDER_TESTING → SUBMITTED → REVIEWED →
APPROVED → COMPLETED → DISPATCHED`، مع حالات استثنائية مثل `REJECTED` و`HOLD`.

## <a id="chain-of-custody"></a> 5. سلسلة الحيازة (Chain of Custody)

سلسلة الحيازة هي **وحدة تدقيق غير قابلة للتعديل (immutable)** تسجّل كل تنقل للعينة بين الأطراف:

- كل حدث يحتوي: العينة، المانح (from user/entity)، المستلم (to user/entity)، الدور، وقت الحدث،
  سبب التنقل، الحالة/الأختام.
- لا حذف ولا تعديل لأي حدث بعد إنشائه؛ يُضاف حدث تصحيحي عند الخطأ.
- الأحداث تشمل: الاستلام، التنسيق، الإسناد، التحويل بين الأقسام، إعادة التحليل، التفريغ.
- يتمكن كل طرف من الإقرار بالاستلام (acknowledge) عبر نقطة API مخصصة.

## <a id="micro-model"></a> 6. نموذج المتطلبات الميكروبيولوجية (n / c / m / M)

يمثل هذا النموذج جوهر تقييم سلامة الأغذية وفق خطة أخذ العينات ذات الفئتين:

| المعامل | المعنى |
| --- | --- |
| **n** | عدد الوحدات/العينات المختبرة في الدفعة |
| **c** | الحد الأقصى لعدد الوحدات التي قد تتجاوز m (ويُعتبر الدفعة مقبولة شريطة أن لا تتجاوز M) |
| **m** | الحد الفاصل (قيمة تستوفي المطابقة إن لم تُتجاوز) — عادةً قيمة منخفضة |
| **M** | الحد الأقصى (تجاوزه في أي وحدة = عدم مطابقة للدفعة مباشرةً) |

### قواعد القرار (للكائن الواحد)

1. **مطابق (COMPLIANT):** جميع الوحدات ≤ m (عدد الوحدات > m لا يتجاوز c).
2. **غير حاسم/مقبول بحدود (INCONCLUSIVE):** عدد الوحدات بين m وM يتجاوز c دون تجاوز أي وحدة لـ M.
3. **غير مطابق (NON_COMPLIANT):** أي وحدة تتجاوز M، أو عدد الوحدات > m يتجاوز c وكانت النتائج تُلزم بذلك.

> التحقق من المنطق النهائي للقواعد بالرجوع إلى ISO 4832 / ICMSF عند التنفيذ، ومحرك التقييم يجب أن
> يكون **قابلاً للضبط (configurable)** وليس منطقاً صلباً في الكود.

### الكيانات

- **Microorganism:** كتالوج الكائنات الدقيقة (code, name_ar/name_en, scientific_name).
- **TestMethod:** طرق الفحص المعتمدة لكل كائن.
- **SamplingPlan:** خطة أخذ العينات المطبقة على المنتج/المواصفة (n, c, m, M لكل كائن).
- **Product/Specification → MicrobiologicalLimit:** يربط المنتج بكل كائن وخطة (n/c/m/M) ووحدة القياس.

## <a id="specifications"></a> 7. المواصفات الميكروبيولوجية وإدارة الإصدارات

- **Specification:** مواصفة وطنية أو مرجعية (كود، اسم عربي/إنجليزي، مرجع المعيار، فئة المنتج).
- **Versioning:** كل مواصفة لها إصدارات؛ الإصدار النشط هو المطبَّق، وأي تعديل يُنشئ إصداراً جديداً
  (لا يُعدَّل التاريخ).
- كل عينة تُقيَّم وفق **الإصدار الساري وقت بدء التحليل** (spec snapshot)، وليس الإصدار الحالي،
  لضمان عدالة النتائج التاريخية.
- صلاحية التعديل/الإنشاء محصورة بدور **مدير التقييم/المشرف**؛ باقي الأدوار تتصفح بقراءة فقط.

---

## <a id="evaluation-engine"></a> 8. محرك التقييم الآلي

- يستقبل نتائج الوحدات المدخلة (MicroUnit results) والحد المطبق (ApplicableLimits).
- يطبّق قواعد (n/c/m/M) ويُخرج: `evaluation` (COMPLIANT / INCONCLUSIVE / NON_COMPLIANT)
  و`evaluation_reason` و`evaluated_at`.
- النتيجة تُعرض لرئيس القسم للمراجعة مع إمكانية تغيير القرار مبرَّراً، ثم للاعتماد.
- يُحفَظ `spec_snapshot` (لقطة الحدود المطبقة) مع كل فحص لضمان إمكانية إعادة بناء القرار.

## <a id="roles"></a> 9. الأدوار والصلاحيات وفصل المهام

فصل المهام يمنع أن يقوم نفس الشخص بأدوار متعارضة على نفس العينة.

| الدور | المسؤوليات الرئيسية | ممنوع منه |
| --- | --- | --- |
| Reception Officer (موظف الاستقبال) | تسجيل العينة، المصدر، قرار الاستلام، إصدار رقم العينة | التحليل/الاعتماد |
| Sample Coordinator (المنسق) | تنسيق العمل، توزيع على الأقسام (benches) | إدخال النتائج |
| Section Head — Chemistry / Micro (رئيس القسم) | إسناد المحللين، مراجعة النتائج، QC، SLA، تقييم (n/c/m/M) | الاعتماد النهائي، إدخال النتائج |
| Analyst / Lab Technician (المحلل) | إدخال النتائج والوحدات، الحفظ والرفع للمراجعة | المراجعة/الاعتماد |
| Lab Director (مدير المختبر) | الاعتماد النهائي للنتائج والشهادات | إدخال النتائج |
| QA Officer (مراجع الجودة) | خط QA مستقل: تدقيق النتائج والمطابقة | الاعتماد |
| Dispatch / Clerk (التفريغ/الكاتب) | طباعة الشهادات والتفريغ للأطراف الخارجية | إدخال النتائج |
| System Admin | إدارة الكتالوجات والأدوار والمستخدمين | عمليات العينات |

النطاق الافتراضي للدور `STATION` (المختبر الاتحادي)، مع إمكانية التوسع للموانئ/المطارات.

## <a id="ui-per-role"></a> 10. تصميمات الواجهات حسب الدور

- **Reception Console:** نموذج تسجيل عينة، اختيار المصدر من الكتالوج، قرار الاستلام، قائمة انتظار
  الاستلام، عرض سلسلة الحيازة.
- **Coordinator Console:** طابور التنسيق، توزيع الأقسام، متابعة حالة العينات.
- **Section Head Console (Chemistry/Micro):** توزيع العينات على المحللين، طابور مراجعة النتائج مع
  عرض الحدود (n/c/m/M) والتقييم الآلي، لوحة QC، لوحة SLA، عارض المواصفات (قراءة فقط).
- **Analyst Console:** قائمة المهام، إدخال النتائج والوحدات، الحفظ كمسودة، الرفع للمراجعة.
- **Lab Director Console:** قائمة الاعتماد، تفاصيل النتيجة والتقييم والحدود، اعتماد/إعادة، إصدار الشهادات.
- **QA Console:** تدقيق عشوائي/منهجي للنتائج، تسجيل مخالفات QC.
- **Dispatch Console:** إصدار الشهادات، التفريغ الخارجي، أرشفة.
- **System Admin:** إدارة الكتالوجات (المصادر، الكائنات، الطرق، المواصفات) والأدوار والمستخدمين.

## <a id="stakeholders"></a> 11. الأطراف الخارجية والتكامل

كل طرف خارجي كيان منفصل يُتكامل عبر API / أحداث / تقارير:

- **الرقابة الغذائية (Food Control)**: نتائج القرارات والمخالفات.
- **التفتيش الميداني (Inspector)**: إدخال عينات التفتيش ومتابعة نتائجها.
- **الترصد (Surveillance)**: بيانات الترصد الغذائي.
- **الجمارك (Customs)**: نتائج العينات المرتبطة بالشحنات للفرز والإفراج.
- **المالية (Finance)**: الفواتير وتحصيل الرسوم والإعفاءات.
- **المعايير (Standards)**: تحديث المواصفات المرجعية.
- **الموانئ والمطارات (Ports/Airports)**: حالة الشحنات والوصولات.

التكامل عبر واجهات برمجة موثقة، وأحداث (events) للتبليغ الفوري، وتقارير دورية مجدولة.

## <a id="next-steps"></a> 12. الخطوات التالية

1. تحويل هذه المواصفة إلى **ERD كامل**:
   `Product → Specification → Microorganism → TestMethod → SamplingPlan (n/c/m/M) →
   Sample → Test → Result/Units → Evaluation → Compliance Decision`.
2. بناء **Django Models** وفق ERD مع Migrations.
3. بناء **Serializers + Viewsets + Guard (RBAC)** وتفعيل فصل المهام.
4. بناء الواجهات حسب تصميمات الأدوار أعلاه.
5. التحقق من محرك التقييم باختبارات حدودية (n/c/m/M) والرجوع إلى ISO/ICMSF.
