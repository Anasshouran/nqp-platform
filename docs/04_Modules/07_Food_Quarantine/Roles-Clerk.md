# 👤 سير عمل دور الكاتب (Food Control Clerk)

> الدور: `CLERK` — وحدة رقابة الأغذية (`04_Modules/07_Food_Quarantine`)
> الإصدار: v2 — مُحدَّث ليطابق التنفيذ الفعلي في `backend/apps/food_quarantine`

دور الكاتب هو نقطة الدخول الإدارية لمعاملات رقابة الأغذية. يوضح هذا المستند خطوات الكاتب من تسجيل الدخول حتى إرسال المعاملة للتحصيل، مع حدود صلاحياته وما يحدث بعدها.

---

## 1. تسجيل الدخول وتوجيه الدور

- يسجّل الكاتب دخوله عبر `POST /api/v1/auth/login/`.
- يتعرف النظام تلقائياً على:
  - **الدور**: `CLERK` *(ملاحظة: الكود الفعلي في النظام هو `CLERK` وليس `FOOD_CONTROL_CLERK`)*.
  - **نطاق العمل** (القطاع/المنفذ): من نموذج `RoleAssignment` في تطبيق `accounts` (ScopeType: SECTOR / PORT / …) — وليس حقل `org_unit_id` مباشرة.
- تظهر له واجهة مخصصة لدور الكاتب عبر `RoleLayout → GenericRoleLayout` بدون أزرار أو قوائم لصلاحيات لا يملكها.

## 2. لوحة التحكم الخاصة بالكاتب

يعرض النظام ملخصاً عن عمله:

- بطاقات إحصائية: وارد اليوم، صادر اليوم، مسودات، قيد المعالجة.
- جدول أحدث المعاملات مع حالتها.
- زر **"إنشاء معاملة جديدة"**.

> ⚠️ **حالة التطبيق**: الصفحة الحالية `/app/clerk-dashboard` (`ClerkDashboardPage.tsx`) هي نموذج أولي ببيانات وهمية (`clerkData.ts`) غير مربوط بالـ API — انظر قسم «حالة التطبيق الحالية».

## 3. إنشاء معاملة (المعالج متعدد الخطوات)

### الخطوة 1: اختيار نوع المعاملة ووسيلة النقل
- نوع المعاملة: وارد / صادر (`FoodShipment.shipment_type`: IMPORT / EXPORT).
- وسيلة النقل: مربوطة بسجل المواعين `Conveyance.conveyance_type` (PLANE / SHIP / TRUCK / REFRIGERATED_TRUCK / RAILCART / CONTAINER / TANKER / OTHER).
- يُعرض المنفذ تلقائياً من حساب الكاتب (غير قابل للتعديل) ويُحفظ في `FoodShipment.port`.

### الخطوة 2: إدخال بيانات الشحنة

تظهر الحقول بناءً على وسيلة النقل. الحقول المخزنة فعلياً على `FoodShipment` اليوم:

| الوسيلة | حقول موجودة في القاعدة | حقول تحتاج `transport_data` (JSON مقترح) |
|---|---|---|
| بحري | `vessel_name`, `loading_port`, `bill_of_lading` | رقم الرحلة البحرية، عدد الحاويات |
| جوي | — | شركة الطيران، رقم الرحلة، مطار الإقلاع، رقم AWB، عدد الطرود |
| بري | — | رقم الشاحنة، رقم اللوحة، المعبر |

- التاريخ (`arrival_date`) والوزن (`total_weight_kg`) مشتركان وموجودان.
- **توصية**: إضافة حقل `transport_data = JSONField(default=dict)` على `FoodShipment` لتخزين الحقول الشرطية دون تعديل مخطط الجداول لكل وسيلة.

### الخطوة 3: البيانات الحكومية
- رقم البيان الجمركي (`customs_number`) — **إدخال يدوي حالياً** (لا يوجد ربط مع الجمارك بعد).
- رقم الشهادة الصحية/الاعتماد (`certificate_no`) ✅ موجود.
- رفع المستندات: اختياري في هذه المرحلة (يحتاج نموذج المرفقات — انظر الخطوة 6).
- الحالة: 🟡 إدخال يدوي / تحقق داخلي.

### الخطوة 4: بيانات المستورد / المصدر
- السجل الفعلي في النظام: نماذج **`Supplier`** (المستورد/المورد) و **`Exporter`** (المُصدِّر) و **`ClearingAgent`** (المخلّص).
- البحث في السجل المسجل مسبقاً؛ إذا لم توجد الشركة يمكن إضافتها (الاسم، الرقم الضريبي، رقم التسجيل، الهاتف، العنوان).
- عند الإرسال تُخزن أسماء الأطراف على الشحنة (`supplier_name`, `exporter_name`, `clearing_agent`).

> 📌 **فجوة**: بنود الشحنة (`FoodOrderItem`) تخزّن اسم المستورد/المورد كنص حر — يُوصى بربطها بـ FK للسجل المركزي لتفعيل سجل المخالفات في محرك المخاطر لاحقاً.

### الخطوة 5: بيانات المنتج
- كتالوج المنتجات موجود: **`FoodProduct`** + `ProductCategory` + `Brand` + `PackageType`.
- اختيار منتج يعرض: التصنيف الغذائي، بلد المنشأ، نوع العبوة.
- إدخال عدد العبوات (`package_count`) والوزن (`weight_kg`) — يمكن إضافة أكثر من صنف.

> 📌 **فجوة**: `_replace_items()` في `views.py` ينشئ البنود كنص حر (`product_name`, `brand`, `origin`) دون FK إلى `FoodProduct`. يُوصى بإضافة `product = ForeignKey(FoodProduct, null=True)` مع الإبقاء على النص كنسخة عرض.

### الخطوة 6: المستندات
قائمة التحقق المقترحة:
- البيان الجمركي، الشهادة الصحية، شهادة المنشأ، الفاتورة، قائمة التعبئة، AWB/B/L، شهادة التحليل (اختياري)، مستند إضافي.

> ❌ **غير منفذ**: لا يوجد نموذج مرفقات في `food_quarantine`. يُوصى بإضافة:
> ```python
> class ShipmentAttachment(BaseModel):
>     shipment = FK(FoodShipment, related_name='attachments')
>     doc_type = CharField(choices=DOC_TYPES)
>     file = FileField(upload_to='food_shipments/%Y/%m/')
>     uploaded_by = FK(user), uploaded_at
> ```

### الخطوة 7: الرسوم (عرض تلقائي)
- الحساب يتم في الخلفية عبر قواعد **`QuarantineFee`** (وليس `FeeRule`) بواسطة الخدمة `compute_fee_breakdown(shipment)` في `services.py`.
- نقطة العرض: `GET /api/v1/food/shipments/{id}/fee-preview/` — تعيد بنود الرسوم والإجمالي.
- أنواع الرسوم: رسوم رقابة، رسوم عينات/معمل، رسوم شهادات (`FoodFee`, `SampleInvoice`, `FoodInvoice`).
- الحالة: 🟡 بانتظار التحصيل (`FEES_DUE`).
- **لا يمكن للكاتب تعديل الرسوم** — لا توجد نقطة نهاية تعديل أساساً.

### الخطوة 8: المراجعة والإرسال
- ملخص شامل للبيانات، ثم أحد الخيارين:
  - **حفظ مسودة** → تبقى الحالة `DRAFT` *(مقترح إضافته — انظر دورة الحالة)*.
  - **إرسال** → `RECEIVED` ثم عند استحقاق الرسوم `FEES_DUE`.

عند الإرسال يقوم النظام تلقائياً (السلوك الحالي في `ShipmentViewSet.create`):
1. حفظ الشحنة مع `recorded_by = request.user` وبناء البنود.
2. تنفيذ `apply_sampling(shipment)` — حساب العينات المطلوبة من سياسات `SamplingPolicy` فوراً.
3. توليد رقم المعاملة — **يدوياً حالياً**: `manifest_number` حقل يدوي فريد؛ يُوصى بمولد آلي بصيغة `FC-YYYY-NNNNN`.
4. تسجيل العملية في `AuditLog` (المستخدم، الدور، المنفذ، نوع الإجراء) ✅ موجود.
5. إشعار المستخدمين المعنيين (أمين الصندوق) عبر تطبيق `notifications` ✅ موجود.

## 4. دورة حالة المعاملة (الحقيقية)

```
[DRAFT*] ──إرسال──▶ RECEIVED ──استحقاق──▶ FEES_DUE ──سداد──▶ AWAITING_INSPECTION
     │                                                            │
     │                                                       تعيين مفتش
     ▼                                                            ▼
  تعديل مسودة                                            UNDER_INSPECTION
                                                                   │
         ┌──────────────── أخذ عينات ○ لا ────────────────────────┤
         ▼                                                        │ نعم
   AWAITING_DECISION ◀── AWAITING_LAB_RESULTS ◀── عينات + تحليل ──┘
         │
         ├── RELEASED (إفراج)            ├── HOLD (حجز)
         ├── CONDITIONAL_RELEASE         ├── RE_EXPORT (إعادة تصدير)
         ├── PARTIAL_RELEASE             ├── DESTROYED (إتلاف)
         └── REJECTED (رفض)
(*) DRAFT غير موجود بعد في ShipmentStatus — مقترح إضافته.
```

**تعيين مرجعي مع المصطلحات السابقة:**

| المصطلح القديم | الحالة الفعلية |
|---|---|
| REGISTERED | `RECEIVED` — تم الاستلام |
| AWAITING_PAYMENT | `FEES_DUE` — مستحقة الرسوم |
| PAID | الانتقال إلى `AWAITING_INSPECTION` (السداد عبر `fees_paid` + `FoodInvoice`) |
| ASSIGNED_INSPECTOR | ضبط `assigned_inspector` (الحالة تبقى بانتظار التفتيش/تحتها) |
| SAMPLING | إنشاء `FoodSample` + `ChainOfCustody` |
| LABORATORY | `AWAITING_LAB_RESULTS` |
| UNDER_REVIEW | `AWAITING_DECISION` |
| COMPLETED | `RELEASED` (أو أي قرار نهائي آخر) |

صلاحيات الكاتب على الحالات فقط:
- إنشاء `DRAFT`.
- تعديل `DRAFT`.
- إرسال `DRAFT` → `RECEIVED`.

بعد الإرسال يرى الكاتب الحالة في قائمته وشريط الحالة في صفحة التفاصيل، **بدون** أي أزرار للمراحل التالية (تحصيل، تعيين مفتش، تفتيش، عينات، مختبر، قرار).

## 6. تكامل سير العمل مع باقي الأدوار (بأسمائها الفعلية)

1. **ACCOUNTANT / أمين الصندوق**: يؤكد السداد → `fees_paid=True` والانتقال لـ `AWAITING_INSPECTION`.
2. **PORT_OFFICER / مدير المنفذ**: يعيّن مفتشاً (`assigned_inspector`).
3. **FOOD_INSPECTOR**: التفتيش الميداني (`FoodInspection`) وقد يسجل عينات.
4. **LAB_RECEPTIONIST**: استقبال العينات في المختبر.
5. **LAB_TECHNICIAN / CHEM_ANALYST / MICRO_ANALYST**: تنفيذ التحليل وإدخال النتائج (`SampleTest`).
6. **CHEM_SECTION_HEAD / MICRO_SECTION_HEAD / LAB_DIRECTOR**: اعتماد النتائج (`ResultEvaluation`).
7. **FOOD_DIRECTOR**: مراجعة الملف وإصدار القرار النهائي (`final_decision`).
8. **الجمارك**: الاطلاع على قرار الإفراج عبر شهادة الإفراج.

كل خطوة تُسجل في `AuditLog` وتحدّث `status` على الشحنة.
